# Orbitloom 需求与目标

更新日期：2026-10-30

状态：首版需求和主界面方案已确认，尚未实现。

## 1. 产品定位

Orbitloom 是供个人使用的 macOS 脚本与项目管理、运行工具。

用户经常下载脚本或 Git 项目，文件分散在多个位置。时间久了，容易忘记项目的用途、位置、运行环境，以及启动和停止方式。

产品目标是：让用户找得到、看得懂、用得起曾经下载的脚本和项目。

核心价值：

- 不必记住项目存放在哪个目录，可以按名称或用途找到它。
- 不必每次重新阅读文档、查找环境和整理运行命令。
- 已经配置成功的项目，后续能够一键启动、查看日志和停止。

## 2. 已确认的范围与优先级

| 优先级 | 内容 | 范围 |
| --- | --- | --- |
| P0：首版 | 多目录项目发现 | 添加多个扫描位置，发现项目与独立脚本，保留原始位置 |
| P0：首版 | 本地信息提取 | 提取用途、运行环境、依赖声明及运行命令，支持手动补充和修正 |
| P0：首版 | 配置保存 | 首次确认后保存可用的运行配置，重新扫描时保留用户修改 |
| P0：首版 | 启动与停止 | 一键启动和停止，展示运行状态与日志 |
| P0：首版 | 项目列表与基础搜索 | 统一展示项目，按名称或用途查找 |
| P1：后续完善 | 管理便利性 | 标签、最近使用记录等增强功能 |
| P2：最后考虑 | 共享依赖复用 | 减少重复下载和存储，不影响首版交付 |

首版支持 Python、Node.js 和 Shell。Git 仓库是项目来源与组织方式，具体运行规则仍取决于项目类型。

首版采用本地文件和明确规则解析，不接入在线或本地 AI 模型。Docker 等其他项目类型后续再扩展。

首版面向个人使用，不包含账号体系或多人协作。优先使用各项目已有的运行环境，暂不自动安装环境或依赖。

## 3. 项目发现与收录

### 3.1 扫描来源

- 用户可以添加多个扫描目录，例如下载目录、桌面和代码目录。
- 用户主动扫描指定目录下的子目录，查看候选的名称、路径、类型和识别依据，勾选后才添加到资料库。
- 应用启动时只刷新已收录项目的识别信息和路径存在状态，不自动发现或添加新项目。保存扫描目录不触发扫描。
- 支持从资料库旁的添加入口手动选择单个项目目录或独立脚本，填写名称（必填）和用途（可选），确认保存后才收录。取消不收录；重复路径可直接打开已有条目，不覆盖原有资料和配置。
- 保留项目原始位置，Orbitloom 统一维护项目索引和运行配置，不要求搬迁文件。

### 3.2 收录规则

- 跳过 `node_modules`、虚拟环境、构建产物等无关目录。
- 项目内部的普通脚本先归属于该项目，避免全部作为独立条目收录。
- Maven、Gradle 声明也作为项目边界；`mvnw`、`gradlew` 等构建包装脚本不作为独立扫描候选，仍允许手动添加。
- 候选默认不勾选，取消或关闭候选预览不会收录项目。已收录路径不重复展示，从资料库移除的项目必须重新勾选才会再次收录。
- 同一个路径被多个扫描目录覆盖时，只收录一次。
- 位于不同路径的项目副本保留为不同条目。
- 文件被移动或删除后，标记“原位置不存在”，保留已有备注和运行配置，并允许重新定位。

扫描由用户打开「扫描发现」或在预览中重新扫描触发；不做定时扫描或文件监听。具体项目边界规则见 implementation.md。

## 4. 本地信息提取与项目配置

### 4.1 项目信息

| 信息 | 提取或配置方式 |
| --- | --- |
| 名称与类型 | 从目录、项目配置或脚本中识别，支持修正 |
| 用途简介 | 从 README、项目描述或脚本头部注释提取；缺失时手动补充 |
| 来源与位置 | 记录本地路径；存在 Git 远程地址等来源信息时提取 |
| 运行环境 | 读取版本声明、依赖文件和已有环境配置 |
| 启动配置 | 保存启动命令、工作目录、必要参数和环境选择；记录可识别的必要环境变量名称 |
| 停止配置 | 使用应用记录的运行进程，或项目明确配置的停止命令 |
| 备注 | 支持补充使用说明，并在重新扫描时保留 |

### 4.2 识别原则

- 优先提取项目明确声明的命令和环境信息。
- 展示识别信息的来源，区分提取结果与用户确认过的配置。
- 存在多个启动入口时，由用户选择默认入口。
- 无法确定的信息标记为“待配置”，提供手动编辑入口。
- 首次运行前由用户检查并确认必要配置；保存后可重复一键使用。
- 后续扫描不得直接覆盖用户修改过、确认可用的命令和备注。
- 扫描和解析本身不执行项目命令。

没有说明文档、缺少标准配置的脚本，可能无法自动识别用途和正确启动方式。首版允许首次手动配置，不承诺所有项目都能自动完成配置。

## 5. 启动、停止与运行反馈

### 5.1 启动

- 按已保存的命令、工作目录和运行环境启动项目。
- 优先使用项目已有环境。
- 缺少环境、依赖或必要配置时，明确提示缺失项，允许用户修正后重新启动。
- 显示运行状态并提供日志，帮助用户判断是否启动成功及失败原因。

### 5.2 停止

- 支持停止由 Orbitloom 启动并明确归属于该项目的运行实例。
- 根据项目配置结束对应进程，或执行明确配置的停止命令。
- 停止操作应限定到对应运行实例，避免影响其他项目或无关程序。

### 5.3 状态区分

- 区分未运行、运行中、执行完成和失败等状态。
- 一次性脚本正常执行结束属于完成，不应统一显示为失败。
- 常驻服务需要持续运行，异常退出应提供对应日志和反馈。
- “待配置”和“原位置不存在”属于项目可用性信息，应与运行状态区分展示。

首版支持应用内查看运行日志；日志保留时长、交互式命令支持范围及应用退出后的进程处理方式，尚未确定。

## 6. 主界面方案

主窗口采用左侧项目列表、右侧项目详情的结构。

### 6.1 项目列表

- 统一展示收录的项目。
- 展示名称、用途、类型、路径和运行状态。
- 提供按名称或用途查找项目的基础搜索。
- 项目可添加多个标签，列表展示标签，并支持「全部／无标签／具体标签」单选过滤；过滤与名称、用途搜索同时生效。
- 批量选择仅作用于当前搜索及标签过滤结果，切换条件时取消隐藏项目的勾选。

### 6.2 项目详情

- 展示用途、来源、位置和运行环境。
- 展示全部项目标签，并提供独立编辑入口；支持添加、移除和复用已有标签，不要求先完成运行配置。
- 查看并修改启动、停止等运行配置。
- 查看日志及失败信息。
- 启动和停止按钮保持在固定位置。

### 6.3 目录内脚本

- 收录目录后，在「文件」页签按需查看当前层文件，支持进入子目录、返回上级、回到根目录和刷新。
- 点击 Python、Node.js、Shell 脚本进入独立面板，自动填入启动命令，首次核对并保存配置后可启动。
- 各脚本分别保存工作目录、参数、运行环境与停止配置，分别展示状态和最近一次日志；左侧仍只收录所属目录。
- 脚本执行结果在主窗口底部从下往上展开的抽屉中展示，包含脚本名称、状态、实时日志、停止与复制日志操作。启动后自动展开；关闭或按 Esc 收起抽屉不会停止脚本。
- 脚本详情和配置编辑沿用现有面板；从详情启动或查看结果时先关闭详情面板，再展示结果抽屉。文件列表及已配置脚本提供独立「查看结果」入口。
- 默认工作目录为脚本所在目录，自动生成的命令使用脚本绝对路径，允许用户另选工作目录。
- 文件页提供「已配置脚本与历史日志」入口。文件失效时保留配置与日志，并允许停止尚在运行的实例。
- 目录及其中脚本有活动实例时，禁止移除或重新定位该目录；应用退出时沿用已有实例清理流程。
- SQL 文件展示「需要数据库执行环境」，本次不提供数据库连接与 SQL 执行。其他不支持的文件仅展示类型提示及 Finder 定位入口。

扫描目录管理放在设置中。

标签功能作为本次确认的 P1 增量实现。手动添加项目时可选填标签；中英文逗号和换行用作分隔符，保存时去掉首尾空白、空标签及完全相同的重复标签。标签区分大小写。旧资料库中没有标签字段的项目按无标签处理，刷新及重新定位保留标签。标签的修改和删除只作用于当前项目，暂不提供全局重命名或多标签组合筛选。

## 7. 核心使用流程

### 7.1 首次收录与使用

手动添加项目，或扫描发现 → 预览并勾选候选 → 添加所选 → 检查识别结果 → 补齐并保存必要配置 → 启动 → 根据状态和日志确认运行结果 → 按需停止。

### 7.2 后续使用

按名称或用途搜索 → 选择项目 → 一键启动 → 查看状态和日志 → 按需一键停止。

### 7.3 无法直接使用时

- 信息缺失：提示待配置，允许手动补充。
- 环境或依赖缺失：说明缺失项，由用户准备好环境后再运行。
- 启动失败：展示失败状态和日志，允许修正运行配置。
- 原路径失效：保留条目与配置，允许重新定位。

## 8. 首版验收标准

以下是待实现后的需求验收标准，不代表已经执行检查或测试。

1. 可以添加多个扫描目录，预览其中的项目或独立脚本，勾选后才收录；启动、刷新和仅扫描都不会自动新增条目。
2. 同一路径不会因扫描目录重叠而重复收录；不同路径的项目副本能够独立管理。
3. 可以从本地文档和配置提取可识别的信息，对缺失内容提供手动配置入口。
4. 确认过的运行配置能够保存，重新扫描后仍保留用户修改。
5. 在运行环境具备、配置正确的前提下，可以一键启动并查看日志；运行中的项目可以一键停止，且不会停止无关实例。
6. 一次性脚本正常结束显示为完成；失败时可以看到对应反馈。
7. 项目文件移动或删除后，已有信息不会直接丢失，并支持重新定位。
8. 一个已经配置成功的项目，过段时间后仍能按名称或用途找到，并且不必重新查文档、找环境或输入命令即可使用。

## 9. 低优先级需求：共享依赖复用

该需求最后再做，不纳入首版验收。

用户希望不同项目存在依赖交集时，优先使用已有依赖，减少重复安装的成本。

后续方案建议遵循以下方向，具体工具和机制尚未确定：

- 对兼容依赖复用本地存储，减少重复下载和磁盘占用。
- 各项目保留独立的依赖版本和运行环境，避免一个项目升级后影响其他项目。
- 名称相同但版本、运行时或构建条件不兼容的依赖分别保留。
- 新项目仍可能需要建立链接、生成入口等环境配置，不能将复用等同于完全跳过配置。
- 优先评估成熟包管理工具的能力；pnpm、uv 仅作为候选，不是当前技术决策。

## 10. 建议的后续实施顺序

以下是实施建议，不表示已经开始开发或完成技术选型：

1. 完成手动添加项目、编辑和保存运行配置。
2. 完成启动、状态、日志和停止的完整使用流程。
3. 接入多目录自动发现、本地信息提取和基础搜索。
4. 完善主界面、设置和异常反馈，并根据实际项目细化各类型的识别规则。

实施前仍需具体化：配置持久化方式、扫描触发策略、各类型的命令与环境识别规则、进程生命周期管理，以及用于针对性验证的实际项目样例。

开发和验证应遵守项目协作规则：先检查现有实现，明确修改与验证范围；不采用 TDD，不自动运行回归测试。
